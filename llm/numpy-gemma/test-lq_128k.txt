# Technical Report: `np_gemma` Qwen3.8-Flash-Next Runtime

## 1. Architecture Overview

This runtime implements Qwen3.8-Flash-Next (Qwen4exp) using NumPy for reference logic and custom C/CUDA kernels for performance. It supports both CPU execution (via OpenMP and AVX-512) and GPU execution (via CUDA), with a hybrid MoE strategy that splits expert computation between the GPU and CPU based on memory and usage patterns.

### 1.1 GGUF Reader and NVFP4 Converter

**File:** `np_gemma/gguf.py`, `np_gemma/st_qwen4.py`

**GGUF Reader (`gguf.py`):**
*   **Function:** `open_gguf(path)` detects if the file is split (`GGUFSplit`) or single (`GGUF`).
*   **Data Flow:** The reader maps the file into memory (`mmap`). It parses metadata and the tensor directory. `raw(gname)` returns a view of the quantized blocks (e.g., Q8_0, BF16, NVFP4) without copying. `dequant(gname)` converts these blocks to `float32` on demand.
*   **Key Implementation:** `_dequant()` handles specific block formats (Q4_0, Q8_0, BF16, etc.). For NVFP4 types (NV4, NVX, E4M3_ROWS), it uses specialized row-byte calculations (`_ROW_BYTES`).

**NVFP4 Converter (`st_qwen4.py`):**
*   **Function:** `NVFP4Source` provides a GGUF-like interface to NVIDIA ModelOpt safetensors checkpoints.
*   **Data Flow:** It reads `model.safetensors.index.json` to locate weights. It converts routed experts (NVFP4 4-bit codes + E4M3 scales) into the runtime's `KQ_NVX` or `KQ_NV4` layout using `cops.kq_nvx_pack` or `cops.kq_nv4_pack`. Large BF16 matrices are kept as-is or requantized to Q8_0.
*   **Key Implementation:** `_make(gname)` dispatches conversion based on tensor type. `ple_rows()` handles the n-gram table by gathering random rows from memory-mapped shards, optimizing for random access patterns with `madvise(MADV_RANDOM)`.

### 1.2 Program of Records and CPU Interpreter

**File:** `np_gemma/program.py`, `np_gemma/csrc/bf16_linear.c` (implied via `cops`)

**Program of Records:**
*   **Function:** `Program` class builds a flat list of operations (`recs`). Each record is an opcode and operands (addresses, slots, constants). `finish()` serializes this into an `int64` array (`buf`) containing a header, environment (slots), and records.
*   **Data Flow:** Python code (e.g., `compile_qwen4_step`) emits records like `KQ_LINEAR`, `HC_NORM`, `ATTN_QSA`. These records reference host memory addresses. The `bind()` method updates slot values (e.g., `pos`, `cos`, `sin`) before execution.

**CPU Interpreter:**
*   **Function:** `Program.run()` calls `cops.gp_run(buf, limit)`, which executes the records in C.
*   **Data Flow:** The C runner iterates through records. For each, it fetches operands from the environment or literal values and calls the corresponding C kernel (e.g., `kq_linear` for matrix multiplication, `hc_norm_body` for grouped RMS norm).
*   **Key Implementation:** `run_py()` provides a Python fallback interpreter for debugging, calling individual C entry points for each record. `profile()` measures time per record.

### 1.3 MoE Layer on the CPU

**File:** `np_gemma/csrc/kquants.c`, `np_gemma/csrc/moe.c`

**Function:** `kq_moe()` in `kquants.c` orchestrates the MoE computation.

**Data Flow:**
1.  **Routing:** `ROUTER_TOPK` record computes expert indices and weights.
2.  **Sorting:** `moe_sort_pairs()` (in `moe.c`) sorts token-expert pairs by expert ID to group computations.
3.  **Gate/Up Projection:** For each used expert, `kq_rows_n()` computes `gate_proj` and `up_proj` using optimized kernels for the weight format (Q8_0, NVX, etc.).
4.  **Activation:** `silu(gate) * up` is computed, and the result is quantized to int8 for the down projection.
5.  **Down Projection:** `kq_rows_n()` computes `down_proj`.
6.  **Combination:** `moe_combine()` sums the outputs of the selected experts weighted by their routing scores, adding the shared expert output if present.

**Key Implementation:** The code uses OpenMP for parallelism. `kq_tile4()` optimizes for 4x4 tiles of rows and tokens to leverage AVX-512 VNNI instructions (`vpdpbusd`).

### 1.4 GPU Path

**File:** `np_gemma/qwen_gpu.py`, `np_gemma/qwen4_gpu.py`, `np_gemma/gpu.py`

**Hot Experts:**
*   **Function:** `QwenGPU.__init__` and `_store()` allocate GPU buffers for a subset of experts ("hot" experts). `HotCache` dynamically swaps experts based on usage frequency.
*   **Data Flow:** During a step, `HOT_SPLIT` identifies which selected experts are hot (on GPU) and which are cold (on CPU). `KQ_HOT_MOE` computes hot experts on the GPU. A CPU program (`CPU_JOIN`) computes cold experts in parallel. Results are summed (`ADD`).

**Mixed Groups:**
*   **Function:** `Qwen4GPU._moe_mix()` handles large prompt chunks.
*   **Data Flow:** `MOE_PLAN` (in `moe.c`) decides how to split experts between GPU and CPU based on token counts and memory. The GPU copies selected experts to a ring buffer (`mix_ring`). The GPU computes hot and copied experts, while the CPU computes the rest. Results are combined.

**Copies:**
*   **Function:** `FETCH`, `FETCH_WAIT`, `FETCH_DONE` records manage asynchronous copies of expert weights from host to device using CUDA streams and events.

### 1.5 QSA Attention and Indexer

**File:** `np_gemma/qwen4.py`, `np_gemma/csrc/qsa.c`

**Indexer (`QSA_SELECT`):**
*   **Function:** `qsa_select_body()` in `qsa.c`.
*   **Data Flow:** It computes raw keys for new tokens. For complete blocks of `ratio` tokens, it computes a block key (mean of raw keys, RMS norm, RoPE). For each query, if the context exceeds the budget, it scores all block keys using `relu(q . k)`, selects the top `budget` blocks, and creates a selection mask (`sel`).

**Attention (`ATTN_QSA`):**
*   **Function:** `attn_qsa_body()` in `qsa.c`.
*   **Data Flow:** It performs attention only over the selected keys (and the tail of the context) using the int16 KV cache. This reduces computation for long contexts.

### 1.6 Hyper-Connections and N-gram (PLE) Layer

**File:** `np_gemma/qwen4.py`, `np_gemma/csrc/hyperconn.c`

**Hyper-Connections (`HC_*`):**
*   **Function:** `hc_pre()` in `qwen4.py` and `hc_norm_body`, `hc_mix_body`, `hc_add_body` in `hyperconn.c`.
*   **Data Flow:** The residual stream is split into `hc_count` streams. `HC_NORM` applies grouped RMS norm. A low-rank gate (`down`/`up` projections) computes mixing weights. `HC_MIX` computes the block input as the mean of gated streams. `HC_ADD` injects the block output back into each stream with a learned weight.

**N-gram (PLE) Layer:**
*   **Function:** `ple()` in `qwen4.py` and `ple_gate_body`, `ple_conv_body` in `hyperconn.c`.
*   **Data Flow:** `ple_ids()` computes hashes of n-grams. `ple_rows()` fetches embeddings from the n-gram table. `PLE_GATE` computes a gate from the embeddings and the current streams. `PLE_CONV` applies a dilated depthwise convolution to the gated values and adds the result to the residual streams.

### 1.7 MTP (Multi-Token Prediction)

**File:** `np_gemma/qwen4.py`, `np_gemma/qwen4_gpu.py`

**Function:** `Qwen4.mtp()` and `Qwen4GPU.mtp()`.

**Data Flow:**
1.  **Drafting:** The MTP layer takes the hidden states from the previous step and predicts the next token. It uses a separate cache (`Qwen4MTPCache`).
2.  **Verification:** The main model verifies the drafted tokens in a single forward pass (`verify()`).
3.  **Commit:** `commit()` updates the main model's cache and state only for the accepted tokens. The MTP cache is updated with the verified states.

## 2. KQ_NVX Layout Explanation

The `KQ_NVX` layout is designed for NVFP4 experts to optimize both CPU AVX-512 VNNI kernels and GPU Tensor Cores.

**Byte-by-Byte Structure (per group of 16 rows):**

1.  **Header (16 bytes):**
    *   Bytes 0-3: `float32` global scale (`g`) for the matrix.
    *   Bytes 4-15: Padding/Zeros.

2.  **Blocks (for each block of 32 columns):**
    *   **Steps (8 steps, 32 bytes each, total 256 bytes):**
        *   Each step `s` (0-7) holds 4 values (indices `4s` to `4s+3`) for all 16 rows.
        *   Byte `4r + u` (where `r < 8`) contains the 4-bit code for row `r` in the low nibble and row `r+8` in the high nibble.
        *   This interleaving allows a single `vpdpbusd` instruction to process 4 values for 16 rows (8 lanes of 2 rows each) or 2 rows per lane on GPU.
    *   **Scales (32 bytes):**
        *   Bytes 256-271: E4M3 scales for values 0-15 of the 16 rows.
        *   Bytes 272-287: E4M3 scales for values 16-31 of the 16 rows.

**Why it suits CPU and GPU:**

*   **CPU (AVX-512 VNNI):** The `vpdpbusd` instruction multiplies unsigned 8-bit integers (codes + 12) with signed 8-bit integers (quantized x) and accumulates into 32-bit integers. The layout allows loading 4 bytes of x (broadcast) and 64 bytes of weights (16 rows x 4 values) to perform 16 dot products in one instruction. The scales are applied in float32 after the integer accumulation.
*   **GPU (Tensor Cores):** The 4-byte chunks for 2 rows align with the fragment layouts of Tensor Cores (e.g., `mma.sync` for fp16/int8). The interleaving ensures that the data for adjacent rows is contiguous, facilitating efficient shared memory loads and register usage.

## 3. Ten Risks or Bugs

1.  **Memory Leak in `Mirror.add`:**
    *   **File:** `np_gemma/gpu.py`, `Mirror.add()`
    *   **Issue:** If an array is added multiple times, `bisect.insort` might insert duplicate starts, or the `arrays` dict might not handle views correctly if the base array is garbage collected.
    *   **Fix:** Ensure `start` is checked against existing entries before insertion. Use weak references or explicit ownership tracking for arrays.

2.  **Race Condition in `HotCache` Updates:**
    *   **File:** `np_gemma/gpu.py`, `HotCache`
    *   **Issue:** Concurrent updates to `slots` and `dslots` during `prepare()` and `observe()` might lead to inconsistent state if not properly synchronized with CUDA streams.
    *   **Fix:** Use CUDA events to synchronize host updates with device execution.

3.  **Integer Overflow in `kq_x16_body`:**
    *   **File:** `np_gemma/csrc/kquants.c`, `kq_x16_body()`
    *   **Issue:** `size_t n = (size_t)t * cols;` might overflow if `t` and `cols` are large, leading to incorrect memory allocation or access.
    *   **Fix:** Check for overflow before allocation. Use `int64_t` for intermediate calculations.

4.  **Incorrect RoPE Application in `qsa_select_body`:**
    *   **File:** `np_gemma/csrc/qsa.c`, `qsa_select_body()`
    *   **Issue:** The RoPE angles for block keys are computed using `b * ratio` as the position. If the block is not aligned to the start of the context, this might be incorrect.
    *   **Fix:** Verify that the position used for RoPE matches the actual position of the first token in the block.

5.  **Inefficient Memory Access in `ple_rows`:**
    *   **File:** `np_gemma/st_qwen4.py`, `ple_rows()`
    *   **Issue:** `cops.kq_gather` uses `memcpy` for each row. For very small rows, this overhead might be significant.
    *   **Fix:** Use vectorized loads or batched copies if the row size is small.

6.  **Hardcoded `KQ_NV4_MAX`:**
    *   **File:** `np_gemma/csrc/kquants.c`, `kq_dot_nv4()`
    *   **Issue:** `KQ_NV4_MAX` is hardcoded to 4096. If `cols` exceeds this, the stack-allocated arrays `aw` and `sc` will overflow.
    *   **Fix:** Dynamically allocate these arrays or add a check to fall back to a slower path if `cols > KQ_NV4_MAX`.

7.  **Potential Division by Zero in `kq_quant_part`:**
    *   **File:** `np_gemma/csrc/kquants.c`, `kq_quant_part()`
    *   **Issue:** `float inv = m > 0.f ? 127.f / m : 0.f;` is safe, but `xs[g] = m / 127.f;` could lead to precision issues if `m` is very small.
    *   **Fix:** Add a minimum threshold for `m` to avoid denormalized numbers.

8.  **Inconsistent State in `Qwen4GPU.commit`:**
    *   **File:** `np_gemma/qwen4_gpu.py`, `commit()`
    *   **Issue:** The function updates `cache.ple_ids` and `cache.ple_conv` on the host but might not synchronize with the GPU cache if `cache_dev` is not properly updated.
    *   **Fix:** Ensure `cache_dev.buffer(...).upload(...)` is called for all modified state arrays.

9.  **Missing Error Handling in `gg_load`:**
    *   **File:** `np_gemma/gpu.py`, `GPUProgram.__init__()`
    *   **Issue:** If `gg_load` fails, the error message might not be captured correctly if `gg_last_error` is not thread-safe or if the error is overwritten.
    *   **Fix:** Capture the error immediately after the call and store it.

10. **Suboptimal Thread Scheduling in `kq_moe_body`:**
    *   **File:** `np_gemma/csrc/kquants.c`, `kq_moe_body()`
    *   **Issue:** `omp_set_schedule` is called inside the parallel region, which might not be effective or might cause overhead.
    *   **Fix:** Set the schedule before the parallel region or use `schedule(runtime)` with a pre-set schedule.

## 4. Plan to Speed Up Prompt Pass on 8GB GPU

**Goal:** Increase throughput for prompt processing (prefill) on a GPU with 8GB free memory.

1.  **Optimize Expert Copying with Ring Buffer Tuning:**
    *   **Action:** Reduce `MIX_KEEP` and `MIX_KEEP_MIN` to allow a larger `mix_ring` buffer, enabling more experts to be copied to the GPU simultaneously. Adjust `MIX_GPU` cost model to favor more GPU experts.
    *   **Expected Gain:** 15-20% reduction in prompt time by reducing CPU-GPU synchronization stalls.

2.  **Implement Tensor Core Acceleration for Dense Matrices:**
    *   **Action:** Ensure `NP_GEMMA_GPU_TC=1` is enabled and verify that dense BF16/Q8_0 matrices are converted to formats suitable for Tensor Cores (e.g., fp16). Use `gg_set_tc` to enforce Tensor Core usage for large matrix multiplications.
    *   **Expected Gain:** 30-40% speedup for the dense part of the prompt pass.

3.  **Increase Mixed Group Size:**
    *   **Action:** Increase `MIX_SIZE` from 1024 to 2048 or 4096, if memory allows. This reduces the number of `MOE_PLAN` calls and improves amortization of copy overheads.
    *   **Expected Gain:** 10-15% reduction in overhead for long prompts.

4.  **Prefetch Expert Weights:**
    *   **Action:** Implement asynchronous prefetching of expert weights for the next layer while the current layer is being computed. Use CUDA streams to overlap copies with computation.
    *   **Expected Gain:** 20-25% reduction in total time by hiding copy latency.
