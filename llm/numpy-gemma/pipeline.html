Gemma 4 26B-A4B in NumPy

A from-scratch runtime whose only dependency is NumPy, built to be verified against Hugging Face and then made fast enough to serve a coding agent. Every number below is measured on the same machine unless it says otherwise. The story is a chain of tradeoffs: each stage buys speed or memory and pays for it in numerical quality — and the quality bill is usually paid by the MoE router.

Sliding heads. 25 of the 30 layers attend only to the last 1024 keys and use a 256-wide head with 8 KV heads; the 5 global layers use a 512-wide head with 2 KV heads and attend to everything. The GGUF says so explicitly, in gemma4.attention.sliding_window_pattern. This one fact is what makes long context affordable — and it is the reason the attention work below splits cleanly into "wins" and "loses".

The router. Each layer routes to 8 of 128 experts with an argmax. Any change to summation order perturbs the hidden state by a few ULPs, the router picks a different expert, and the difference is amplified to a few percent. That is why almost no optimisation here is bit-exact, and why the test that matters is the greedy token, not the logit vector.

06

Attention — where long context is won and lost

performancequality

Three changes, in increasing order of ambition: drop the keys the window hides before building scores; write that as a C flash kernel; and use the kernel only where it wins.

a. Key slice in the plain path

The GGUF says which layers slide. The plain path used to score all n keys and mask afterwards; it now slices [lo, hi] so masked keys are never scored. Exact in the real numbers — a dropped key is masked for every query in the block — but not bit-exact, because the second matmul now sums over fewer terms.

Quality: greedy tokens 8/8 identical at every size, though layer-0 attention already differs by 5.6×10−5 relative and the router flips an expert at layer 1. The drift is rounding, not masking — the slice is exact in exact arithmetic.

b. C flash kernel

Transposed key, per-block online softmax, block-level causal + window skipping, and a vectorised polynomial exp. Three implementations exist: AVX-512 (16 keys per vector), AVX2 (8), and a straight-C reference. Attention op alone, BLAS given its model-configured 8 threads:

The sliding rows are flat in n — the window caps the work, so 1024 and 4096 keys cost the same. The global rows grow with n and lose to OpenBLAS, because the transposed-key panel does not fit L1 and is re-read once per micro-tile; raising the row tile to fix that starves the load ports. Correctness: all three versions match the NumPy reference to 9×10−8 on well-scaled input and 1.9×10−5 at model magnitudes.

KV cache — memory, and a quality cliff

memoryquality

A sliding layer never reads past its window, so its buffer never needed to grow. It did: the code compacted only on decode steps, so a prompt pass grew all 25 sliding buffers to the full sequence. Compacting during prefill too — keeping window plus the block — bounds them at 2×window + chunk = 2304 rows regardless of context.

Second win: the int8 copy of every key and value was being built even in float mode, where nothing reads it. Gating it on the fused attention removes the difference between the two columns. Together, DSH's ~25k-token prompt goes from roughly 11 GB of cache to 1.9 GB.

The quality cliff: int8 KV is not free

Hidden-state error from quantising each part of the cache independently — the score side (K and the query) dominates, which is the opposite of the naive guess:

value only
0.58%
query only
1.07%
key only
1.39%
all three
1.49%
worst layer
5.6%

1.5% sounds harmless and is not. An error of that size is enough to move the router, and greedy decoding with an int8 cache fell into repeat loops (repeat_len 48) while the identical run on a float cache produced clean text. The diagnosis was confirmed by elimination — greedy+q8 loops, greedy+float does not, temperature 0.7+q8 loops — and the fix was to make float KV the default. The int8 cache decodes faster (102 ms/token vs 164 ms) and is kept as an option, not the default.

The pattern across all eight stages: performance and memory are separable and controllable; quality is where the surprises live, and they almost always arrive through the discrete MoE router rather than through the smooth parts of the network. That is why every optimisation here is gated behind a token-level equality check, and why the int8 KV cache — the one change that broke generation outright — is the only one left off by default.
